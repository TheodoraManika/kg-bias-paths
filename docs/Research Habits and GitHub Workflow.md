# Research Habits and GitHub Workflow

Oct 21, 2026 · @Theodora Manika
Good habits from week 1 make the final report almost write itself: a notebook that explains every result, references that are already checked, and a GitHub organization where every task is an issue and every change a reviewed pull request.
1. Lab notebook
A lab notebook is a dated log of what we ran, why, and what we learned; the run folders store the numbers, the notebook stores the reasoning.
Where: one Markdown file per person per week in the repository (notebook/2026-W45-theodora.md), so it is versioned and searchable.
What to record
	•	What you tried and why (the hypothesis or question)
	•	Which run folders it produced
	•	What you saw, including failures and surprises
	•	What you decided next, and why
Template
## 2026-11-04 — Depth sweep on baseline R-GCN Question: does the parity gap grow with more message-passing layers? Runs: runs/2026-11-04_rgcn_L0..L3_seed0-2 Result: gap rises from layer 0 to 2, flat at 3 (see plot in runs/.../depth.png) Surprise: MRR drops at L3; probably over-smoothing Decision: use 2 layers; add L3 drop to report limitations Next: run decomposition on the 2-layer model
Five minutes at the end of each work session is enough; a missing entry costs hours when writing the report.
2. References
A shared reference library from day one avoids lost papers, duplicate entries and wrong citations at the deadline.
Setup (once)
	•	Both install Zotero and its browser connector.
	•	Create a group library (e.g. "Fair KG LP") on zotero.org and invite each other; add collections: KG embeddings, GNNs, bias in KGs, debiasing, counterfactual fairness, statistics.
	•	Install the Better BibTeX plugin and set it to keep an auto-exported references.bib updated; put that file in the report folder.
	•	Agree a citation-key format (e.g. fisher2020measuring).
Habits
	•	Save papers with the browser connector, not by typing details by hand.
	•	Prefer the published version (conference/journal) over the arXiv version when both exist, and record which one you read.
	•	Add a one-line note per paper: what it shows and why it matters for us.
	•	Verify every reference before citing: open the paper, check title, authors, year and venue. Several references in our planning documents were written from memory and are marked with *; check those first.

5. Set up the GitHub repository
Create the repository
gh auth login gh repo create fairkg-lab/fair-kg-lp --private --clone \   --description "Decomposing and reducing social bias in KG link prediction"
Then add the uv project files, .gitignore, README.md and a licence (MIT is common for research code), and push.
Protecting main
	•	Goal: no direct pushes to main; every change through a reviewed pull request.
	•	On the Free plan, branch protection rules and rulesets are, as far as I know, enforced only on public repositories; private repositories need a paid plan (Team). Check GitHub's current plan page.
	•	Options: make the repository public (fine for code; data stays out of Git anyway), ask whether the university or professor has a GitHub Education organization with Team features, or agree as a team rule never to push to main directly.
Secrets: API keys (e.g. Weights & Biases) never go in the code; use environment variables locally and repository secrets for GitHub Actions.
Free extras for students: the GitHub Student Developer Pack gives each of you GitHub Pro and other tools (link from memory; check current terms).

Naming rules
	•	Scripts that build data are numbered and run in order; each reads only the outputs of earlier steps.
	•	Data files carry their version and settings: people_v1_seed42_rel80.parquet.
	•	Run folders: date_model_variant_seedN.
	•	Configs are named after what they test (cf_direct.yaml), and every run folder stores a copy of its config.
	•	Nothing in notebooks/ is cited in the report; results come only from runs/ via make_figures.py.

8. Creating issues
Every piece of work is an issue before it starts: one clear outcome, one owner, a definition of done, and a link to its phase.
What a good issue looks like
	•	Title: an action with a result, e.g. "Compute degree and award counts on the full graph", not "data stuff".
	•	Small: finishable in 1–3 days; bigger tasks become several issues linked to a parent.
	•	Done when: concrete checks, e.g. "file saved, manifest updated, table in notebook".
	•	Labels, milestone, assignee set at creation.
Issue forms. Add .github/ISSUE_TEMPLATE/task.yml so every issue has the same fields:
name: Task description: A piece of project work labels: [] body:   - type: textarea     id: goal     attributes:       label: Goal       description: What should exist or be known when this is done?     validations:       required: true   - type: textarea     id: done     attributes:       label: Done when       value: |         - [ ]         - [ ]     validations:       required: true   - type: textarea     id: notes     attributes:       label: Notes, links, related issues
Add a second form experiment.yml with fields Hypothesis, Config / runs, Metrics to report and Result, so each experiment issue doubles as its record. A config.yml in the same folder with blank_issues_enabled: false makes everyone use the forms.
Creating issues from the terminal
gh issue create -R $REPO \   --title "Count P21, P27, P106, P166 among humans in Wikidata5M" \   --body "Goal: check the relations we need exist in enough volume.  Done when: - [ ] counts per relation and per gender value in notebook - [ ] decision: P166 or P106 as primary task" \   --label data --milestone "Phase 2: Data and splits" --assignee @me
Seed the backlog in week 1: turn every checkbox of the step-by-step plan into an issue (about 40–50), assigned per the team split. Useful commands: gh issue list -R $REPO --assignee @me, gh issue view 12, gh issue close 12 --comment "Done in #15".
9. Branches, pull requests and review
Every change goes issue → branch → pull request → review → merge, so main always runs and both of us know every part of the code.
	•	Branch from the issue: gh issue develop 12 --checkout creates a branch linked to issue #12 (or git switch -c 12-degree-covariates).
	•	Small commits with clear messages: "Add degree computation on full graph", not "fix".
	•	Open a pull request early (as a draft if unfinished): gh pr create --draft --fill. Write Closes #12 in the description so the issue closes on merge.
	•	Before asking for review: uv run ruff check ., uv run pytest, and the synthetic-graph test pass.
	•	Review: the other person reads the change, runs it if it touches models or metrics, and comments. Review within one working day.
	•	Merge with Squash and merge for a clean history, then delete the branch.
Pull request description template (.github/pull_request_template.md):
Closes #  ## What changed  ## How it was tested - [ ] ruff + pytest - [ ] synthetic-graph check (if model or metric code)  ## Results / screenshots (if an experiment)
Rules: never commit data, checkpoints or API keys; never push straight to main; a change to the shared evaluation module needs both of us to agree.
10. Team rhythm and checklist
A fixed weekly rhythm keeps two people aligned without long meetings.
	•	Weekly meeting (30 minutes): review the board; each person says what finished, what is next, what blocks them; check the plan's decision gates.
	•	Async updates: a short comment on your issues when something changes, instead of messages that get lost.
	•	Weekly integration: merge both branches and run the synthetic tests together.
	•	Monthly: short update email to the professor with progress and open questions.
